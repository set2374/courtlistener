## `cl_sync_incremental_docs` — incremental document sync that preserves embeddings

Added: 2026-08-13. File: `cl/search/management/commands/cl_sync_incremental_docs.py`.

Native-Code-First Review:

- Need: apply an enumerated set of opinion and cluster changes to Elasticsearch without rewriting documents that did not change, and without dropping provider-published embeddings from the ones that did.
- Search: read `cl/search/tasks.py` (`update_es_document` and the `Document.update` call it ends in, `es_save_document`, `get_doc_from_es`, `document_fields_to_update`, and the `"_op_type": "index"` bulk action built by `index_parent_or_child_docs_in_es`), `cl/lib/es_signal_processor.py` (the canonical `update_es_document.si(...)` call site and its embeddings argument), `cl/search/documents.py` (the nested `embeddings` field and `cluster_child = JoinField(...)`), `cl/search/types.py` (the `EventTable` enum), the full option list of `cl/search/management/commands/cl_index_parent_and_child_docs.py`, and `cl_index_embeddings.py` for how a command addresses a MEDIA_ROOT-relative input file. Installed capability checked at the same time: `elasticsearch.dsl` is already a dependency and supplies the partial-update call this rides on, so nothing new is introduced. Note the module path: this tree imports `from elasticsearch.dsl import Document, Q`, the consolidated 9.x layout, not the standalone `elasticsearch_dsl` distribution.
- Native option: the incremental path this application already uses when writes go through the ORM. `Document.update()` for documents already present, which writes only the fields named and therefore cannot disturb a nested field it does not mention; `es_save_document` for documents not yet present.
- Gap: two, precisely. That path is reached through Django `post_save` signals, which bulk raw-SQL writes bypass; and the one non-signal reconciliation mode, `--update-from-event-tables`, covers only `search.Docket`, `search.DocketEntry` and `search.RECAPDocument`, so it cannot be pointed at opinions or clusters. Nothing exposes the incremental path for an arbitrary id list.
- Decision: wrap. The command enumerates ids, resolves each instance, and dispatches the application's own calls. It contains no indexing, mapping, routing or embedding logic of its own: field values come from `prepare()`, the document lookup from `get_doc_from_es`, the write from `elasticsearch.dsl.Document.update`, and the create from `es_save_document`.
- Duplication check: not a parallel indexer. It is the same path `es_signal_processor` takes, reached by an id list instead of a signal. `cl_index_parent_and_child_docs` is not reimplemented or replaced for its actual purpose, which is standing up an index from empty.

Root-Cause Review:

- Symptom: a nightly maintenance run whose change set covered a few thousand rows rewrote roughly 6.6M Elasticsearch documents, stripped their provider vectors, and queued a re-download of 8,638,532 embeddings from S3 that would have taken about nineteen hours.
- Root cause: the run scoped its reindex with `cl_index_parent_and_child_docs --pk-offset min(changed cluster id)`. That flag is a starting offset, not a filter, and the command exposes no upper bound and no id-list option, so the volume of work equalled the corpus above the lowest id the run happened to touch rather than the set of records that changed. This is the underlying source and not a symptom: the size of the sweep, the stripping, and the re-download all follow from it, and each disappears when the scope becomes a list. The `_op_type: "index"` full replace and the absent `prepare_embeddings` are correct design for a backfill; they were only harmful because a backfill was being used for incremental maintenance.
- Evidence: `cl_index_parent_and_child_docs` accepts `--auto-resume`, `--chunk-size`, `--document-type`, `--end-date`, `--missing`, `--non-null-field`, `--pk-offset`, `--queue`, `--search-type`, `--start-date`, `--testing-mode` and `--update-from-event-tables`, and nothing that takes ids. `grep -rn "def prepare_embeddings" cl/` returns nothing, so `prepare()` cannot populate the field. The affected deployment measured 2,370,415 vectored documents against 20,986,976 total on the serving index, and the recovery import's own arguments read `--inventory-rows 8638532`, which is corpus scale rather than change-set scale.
- Scope: the affected class is every reindex invocation scoped by a floor, which is every one this command supports. Bounded counterexamples that stay unchanged: a deliberate whole-corpus rebuild still uses the backfill command and is unaffected; documents not yet in Elasticsearch still take a genuine index here, because they hold no vector to preserve; and RECAP reconciliation continues to use `--update-from-event-tables`, which this does not touch.
- Fix strategy: repair at the source by restoring the invariant that the set of documents rewritten must equal the set of records changed. A floor cannot express that invariant for the general class, because the corpus above it is unbounded and unrelated to the change set; an enumerated id list expresses it exactly for every run. Rejected alternatives were raising the caller's timeout so the re-download could complete, and making the re-import faster, both of which accept the corpus-wide rewrite as given and pay for it more quickly rather than removing it.
- Regression test: the command carries its own runtime canary. It records the vectored-document count by nested-exists before and after itself and exits non-zero if that count fell, which on this path cannot happen, so the check fails loudly if a future change reintroduces a full replace instead of quietly costing another re-download. Per-document errors are collected and also force a non-zero exit, so a partial sync cannot be mistaken for a clean one. Integration coverage for the calling side, including a unit test that fails if the caller reintroduces `--pk-offset` or an open-ended id range, lives with the orchestration that invokes this command.
- Blast radius: additive. A new management command; no existing command, task, signal, document or mapping is modified, so upstream behaviour is unchanged for every caller that does not invoke it. Monitoring is the report file the command writes and its non-zero exit. Rollback is deleting the file and reverting the caller to its previous invocation.
